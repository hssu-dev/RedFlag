# 계획 (보류): Cloud 에이전트의 사이트 직접 탐색

상태: **저장만 함 (2026-11-04, 사용자 지시)**. 착수 전 결정 필요 항목은 맨 아래.

## 문제
실제 피싱은 첫 화면이 아니라 "다음"/"택배 조회" 버튼 뒤에 본체(카드·비밀번호 폼)를 두는 경우가 많다.
현재 Cloud는 에이전트 루프이지만 `sandbox_browse(url)`로 **새 URL만** 열 수 있고(호출마다 새 브라우저),
클릭·스크롤·대기 같은 상호작용과 세션 유지가 없다. (추가 브라우징 2회, 6라운드·45초)

## 설계
- 분석 1건 = 샌드박스 브라우저 세션 1개 유지(Docker, 모바일 Chrome 조건 동일).
- 새 도구:
  | 도구 | 내용 |
  |---|---|
  | `page_state` | 현재 화면 텍스트·숨은 텍스트·폼·**번호 매긴 클릭 가능 요소 목록**·스크린샷 |
  | `click(n)` | n번 링크/버튼 클릭 (코드가 만든 목록의 번호만 허용, 임의 셀렉터 금지) |
  | `scroll` / `wait(s)` | 지연 표시 콘텐츠·카운트다운 |
  | `back` | 이전 화면 |
  | `open(url)` | 같은 세션에서 다른 주소 |
- 탐색 중 발견한 폼(예: 2단계에서 타 사이트로 카드 전송)도 결정적 신호로 점수에 반영. Claude는 계속 증인(점수 X).
- 클릭마다 SSE trace ("3번 '택배 조회' 클릭 → 카드 입력 폼 발견").

## 안전장치
- **입력·제출 금지**: 텍스트 입력 도구 없음. 폼 submit 요소 클릭 차단 + 브라우저 레벨에서 POST/폼 내비게이션 abort.
- 다운로드 차단(시도만 기록), Docker 격리, 사설망 차단 유지.
- 클릭 수·방문 페이지 수·시간 상한. 페이지 텍스트로 지시된 URL은 같은 사이트 또는 코드가 추출한 링크만.

## 대가
- 시간: 현재 약 10–15 s → 30–60 s (Cloud는 백그라운드라 진입은 막지 않음)
- 비용: Opus 호출 분석당 2–3회 → 4–8회

## 착수 전 결정 필요
1. 시간·라운드 상한: 추천 90 s · 10라운드 (현재 45 s · 6)
2. 가짜 데이터 입력(이메일 넣어야 다음 화면) 허용 여부: 추천 **금지 유지, 클릭만**
3. 검증용 데모: 첫 화면 무해 + 버튼 뒤 피싱 폼인 2단계 데모 페이지 추가
