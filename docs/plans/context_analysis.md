# 계획: 맥락 분석기 (Gemma 판단 → 자동 맥락 수집 동의 / 사용자 직접 입력)

상태: 단계 1–3 구현 (2026-11-04, scoring_rules v4). 단계 4(폰 시연·측정) 진행 중. 결과: ../dev-log/PROGRESS.md "v4" 절, eval/followups/REPORT.md.
차별화: 페이지만 보는 판단(Google 고급 보호 등)과 달리, **사용자가 왜·어떻게 이 페이지에 왔는지**를
기기 안의 Gemma가 스스로 판단해 묻고 확인한다. 모든 맥락 단계는 건너뛸 수 있다.

## 0. 원칙
- 모델은 증인, 점수는 코드. 맥락은 점수를 **더하기만** 한다(어떤 맥락도 감점 요인을 지우지 않음).
- Gemma는 화면 문장을 만들지 않는다. 동의 문구·질문은 **정해진 목록의 ID**로만 고른다
  (페이지 인젝션으로 "비밀번호를 입력해 주세요" 같은 창이 뜨는 것 방지).
- 맥락 데이터(앱 정보·대화·사용자 입력)는 분석 중 메모리에만 둔다.
  판정 기록에는 "카카오톡 · 모르는 사람" 같은 요약만 남긴다.
  - **사용자가 직접 건넨 맥락**(상황 설명, 질문 답, 붙여 넣은 메시지)은 사용자가 고급 분석을 누를 때 함께 보낸다(마스킹 적용).
    사용자 결정 2026-11-04. 자세한 내용은 `manual_url_check.md` §5.
  - 자동 수집 대화의 원문은 보내지 않고 판단 enum만 보낸다(추천안).
- **모든 맥락 창에 [건너뛰기]**, 추가로 [다시 묻지 않기]. 건너뛰어도 1차 판정은 그대로 유효.
- 분석 1건당 맥락 요청 최대 1회(자동 수집 1 + 직접 입력 1까지), 같은 사이트는 세션 내 재요청 없음.

## 1. 맥락의 두 종류
| 종류 | 무엇 | 언제 | 화면 |
|---|---|---|---|
| **자동 맥락** | URL을 연 앱, 그 앱에서 링크가 담긴 메시지와 이전 대화 몇 개 | Gemma가 "보면 도움이 된다"고 판단 | **"맥락을 분석해도 될까요?"** 동의 창 → [허용] [건너뛰기] [다시 묻지 않기] |
| **직접 입력 맥락** | 사용자가 쓰는 상황 설명 (자동으로 알 수 없는 것: 전화로 안내받음, 중고거래 중 등) | Gemma가 "사용자 설명이 필요하다"고 판단, 또는 사용자가 원할 때 | **텍스트 입력 창** (질문 1개 + 입력칸 + 빠른 답 칩) → [보내기] [건너뛰기] |

사용자가 먼저 상황을 적고 싶을 수 있으므로, 대기·결과 화면에 **[상황 직접 입력]** 버튼을 항상 둔다
(요청이 없어도 입력 가능 → 같은 직접 입력 맥락 경로로 처리).

## 2. 전체 시퀀스
```
링크 탭 (예: 카카오톡)
 ├─ [자동, 동의 불필요] 출발 앱 분류만 기록 (VIEW 인텐트 referrer: 카카오톡/문자/텔레그램/메일/QR/알 수 없음)
 ├─ Turn 1 (지금과 동일): 페이지 → Gemma 10개 항목 → 1차 점수
 ├─ ① 코드 판단: 제외 / 필요 / 괜찮음
 │    ├─ 제외   → 맥락 단계 없음
 │    ├─ 필요   → ② Gemma는 "어떤 맥락을" 요청할지만 고름 (실패 시 코드 기본값)
 │    └─ 괜찮음 → ② Gemma에게 "맥락이 필요한가?" (두 번째 의견)
 ├─ ② Turn 2: Gemma 도구 호출 → 자동 맥락 요청 / 직접 입력 요청 / 둘 다 / 불필요
 ├─ ③ 자동 맥락: "맥락을 분석해도 될까요?" → 허용 시 출발 앱·대화 수집
 ├─ ④ 직접 입력: 질문 + 텍스트 입력 창 (빠른 답 칩 포함)
 ├─ Turn 3: Gemma 맥락 판단 (시나리오, 목적–페이지 일치, 근거)
 └─ ⑤ 코드가 맥락 규칙으로 가산 → 결과 화면에 맥락 근거 표시
```
검사 건너뛰기·모든 맥락 [건너뛰기]는 이 과정 전체에서 유효(타임아웃 없음).
순서: 자동 맥락을 먼저(사용자 수고 0) → 그래도 부족하면 직접 입력. 둘 다 요청되면 동의 창 → 입력 창 순.

## 3. ① 코드 판단 (결정적)
| 결과 | 조건 | 다음 |
|---|---|---|
| **제외** | 게이트 통과(알려진 정상, 분석 안 함) · 세이프 브라우징 히트 · 이미 85점 이상(차단) · "다시 묻지 않기" | 맥락 단계 없음 ([상황 직접 입력] 버튼만 유지) |
| **필요** | 점수 30–70 · 또는 결제/송금, 신분증, 인증번호, 앱 설치, 지갑 연결 요구 + 출발지가 메신저/문자 | Gemma가 요청 종류·질문만 고름 |
| **괜찮음** | 그 외 (예: 0점이지만 결제 페이지 — 겉보기 정상인 중고거래 안전결제 사칭이 여기에 해당) | **Gemma에게 두 번째 의견** |

## 4. ② Turn 2: Gemma 도구 호출
같은 대화에서 이어서 묻는다(페이지·1차 답을 이미 알고 있어 추가 입력이 적음).

도구:
- `request_auto_context(reasons[])` — 출발 앱·이전 대화를 보고 싶다 (동의 창 띄움)
- `request_user_context(question_id, reasons[])` — 사용자 설명이 필요하다 (입력 창 띄움)
- `no_context_needed(reason)`
- 두 요청을 함께 호출 가능.

reasons (enum, 동의 창 문구로 변환): unexpected_payment, used_trade_payment, app_install, gov_or_refund,
investment, account_threat, brand_unverifiable, delivery, other.

입력: 출발 앱 분류(신뢰), 시간대. 페이지는 여전히 untrusted.
LiteRT-LM 0.18.1 Kotlin에 도구 등록(`ToolProvider`)·자동 호출(`automaticToolCalling`) 존재(AAR 바이트코드 확인).
E4B 도구 호출 형식 준수율은 실험 필요.

### 결정 표
| 코드 | Gemma | 결과 |
|---|---|---|
| 제외 | (묻지 않음) | 맥락 단계 없음 |
| 필요 | 요청 종류 선택 | Gemma가 고른 요청 |
| 필요 | 오류·형식 위반·`no_context_needed` | **코드 기본값**: 출발지가 메신저/문자면 자동 맥락, 아니면 직접 입력(질문은 page_type·requested_actions로 결정) |
| 괜찮음 | 요청 | Gemma가 고른 요청 |
| 괜찮음 | `no_context_needed` / 오류 | 묻지 않음 |
Gemma는 요청을 **추가할 수만** 있고, 코드의 "필요"를 취소하지 못한다.

## 5. ③ 자동 맥락: "맥락을 분석해도 될까요?"
동의 창 내용(정해진 문구 + Gemma가 고른 reason):
> 이 링크는 **카카오톡**에서 열렸어요. **결제를 요구하는 페이지**라, 링크가 담긴 메시지와 앞뒤 대화 몇 개를
> 함께 보면 사기인지 더 정확히 알 수 있어요. 기기 안에서만 확인하고 저장하지 않아요.
> [허용] [건너뛰기] [다시 묻지 않기]

수집 방법:
| 방법 | 얻는 것 | 채택 |
|---|---|---|
| A. 출발 앱 (referrer) | 카카오톡/문자/텔레그램/메일/QR | 항상(분류만), 동의 후 Gemma에게 제공 |
| B. 알림 접근 권한 | 이 링크와 **같은 URL이 담긴 알림**의 보낸 사람 표시명·본문 + 같은 대화의 직전 알림 몇 개 | **기본** (권한 1회 설정; 없으면 동의 창에서 설정 안내) |
| C. 접근성 화면 읽기 | 링크를 누른 순간 메신저 화면에 보이던 대화 몇 줄 | 데모 옵션 (서비스 감시 범위를 메신저까지 넓혀야 함) |
선택: 연락처 권한으로 "보낸 사람이 저장된 연락처인가".
범위 최소화: 링크가 담긴 메시지 1개 + 앞뒤 최대 3개, 각 300자. 전화번호·계좌번호는 마스킹 후 Gemma에 전달.
대화 내용은 사기범이 쓴 글일 수 있으므로 `<untrusted_conversation>`으로 감싼다(페이지와 동일 취급, 지시 아님·증거).
수집 실패(권한 없음, 알림 없음) → 직접 입력 창으로 넘어갈지 Gemma 요청에 따름, 또는 건너뜀.

## 6. ④ 직접 입력 맥락: 텍스트 입력 창
- 질문 1개(정해진 목록에서 Gemma가 고른 ID) + 자유 입력칸 + 빠른 답 칩 + [보내기] [건너뛰기].
| ID | 질문 | 빠른 답 칩 |
|---|---|---|
| U1 | 이 링크를 어떻게 받게 됐나요? | 모르는 사람이 보냄 / 아는 사람이 보냄 / 기관·회사라고 함 / 광고·검색 |
| U2 | 이 사이트에서 무엇을 하려던 참이에요? | 택배 조회 / 결제·송금 / 로그인·본인확인 / 지원금·환급 / 투자 |
| U3 | 전화나 메시지로 이 사이트에 들어가라는 안내를 받았나요? 어떤 내용이었나요? | 예, 전화로 / 예, 문자로 / 아니요 |
| U4 | 중고거래 중이었나요? 상대가 뭐라고 했나요? | 예 / 아니요 |
- 입력은 짧게(최대 300자). 사용자가 받은 메시지를 붙여 넣을 수도 있음 → 사용자 진술은 `<user_statement>`,
  붙여 넣은 메시지는 그 안이라도 지시가 아닌 증거로 취급하도록 시스템 프롬프트에 명시.
- 사용자 진술은 "사용자의 주장"으로 다룬다: 맥락 가산 근거는 되지만 위험 신호를 지우지 않음.
- 음성 입력(키보드 마이크) 그대로 사용 가능.

## 7. Turn 3: Gemma 맥락 판단 항목
- `scenario`: parcel_smishing / used_trade_escrow / gov_voice_phishing / investment_scam / account_threat / romance_or_job / none
- `consistency`: consistent / mismatch / unclear (사용자 목적 ↔ 페이지 요구)
- `sender_risk`: unknown_sender / impersonated_org / known_contact / unclear
- `evidence`: 대화·사용자 진술에서 인용(최대 2)

## 8. ⑤ 맥락 규칙 (scoring_rules, 가산만)
| 조건 | 판정 |
|---|---|
| scenario ≠ none | +25 |
| consistency = mismatch | +20 |
| 전화·메시지 안내(U3 또는 대화) + 앱 설치 요구 | 최소 85 |
| sender_risk = unknown_sender 또는 impersonated_org + 결제·송금 요구 | +20 |
| used_trade_escrow + 결제 페이지 | +25 |
결과 화면: "카카오톡에서 모르는 사람이 보낸 결제 링크예요. 중고거래 사기에 가장 많이 쓰여요." (근거 인용 포함)

## 9. 비용·제약
- 지연: Turn 2(짧은 도구 호출) + Turn 3 ≈ 폰 3–6초 추정(실측 필요). 대부분 사용자 동의·입력 시간과 겹침.
- 알림 접근·접근성으로 타 앱 내용 읽기는 Play 정책 제약 큼 → sideload 데모는 가능, 출시 시 정책 검토.
- 개인정보 고지: 온보딩에 "맥락 분석" 설명과 끄기 스위치.

## 10. 검증
- 마찰: 실제 정상 60건에서 맥락 요청이 뜨는 비율(코드 "필요" + "괜찮음"→Gemma 요청) — Turn 2는 맥에서 오프라인 측정 가능.
- 효과: 시나리오 데모 3종에서 맥락 없을 때 놓치고 있을 때 잡는지
  1. 중고거래 "안전결제" 사칭 + 카톡 대화(알림)
  2. 검찰 사칭 전화 → 원격조종 앱 설치 페이지 + 직접 입력("전화로 안내받음")
  3. 택배 문자 → 카드 결제 요구 페이지
- E4B 도구 호출 형식 준수율, 요청 종류 선택의 적절성, 지연, 건너뛰기 후 동작.

## 11. 단계
1. 출발 앱 자동 분류 + 결과 화면 표시 + [상황 직접 입력] 버튼(직접 입력 경로)
2. ① 코드 판단 + ② Gemma 도구 호출(Turn 2) + 결정 표 + 직접 입력 창 + 맥락 규칙
3. ③ 자동 맥락 동의 창 + B 알림 접근 수집 + Turn 3 대화 맥락 분석
4. 시연 시나리오 3종 + 측정 (C 접근성 대화 읽기는 데모 옵션)
