# 계획: 앱 안 링크 검사 (URL 직접 입력) + 사용자 맥락을 고급 분석에 포함

상태: 단계 1–4 구현 (2026-11-04), 결정 6건은 추천안대로. 단계 5(폰 시연)는 ../dev-log/PROGRESS.md "앱 안 링크 검사" 절.
관련: `context_analysis.md`(맥락 분석기), 메모리 "cloud only on user request".

지금 RedFlag는 **링크를 탭했을 때만** 동작한다(VIEW 인텐트 → LinkHandlerActivity, 또는 Chrome 접근성 덮개).
두 가지를 더한다.
1. **앱 안 검사**: 링크를 열지 않고 먼저 확인한다. 받은 메시지를 통째로 붙여 넣어도 된다.
2. **사용자 맥락 → 고급 분석**: 사용자가 직접 건넨 맥락(직접 입력한 상황 설명, 붙여 넣은 메시지)은
   사용자가 고급(정밀) 분석을 누를 때 **함께 보낸다**(사용자 결정 2026-11-04). 자동 전송은 여전히 없다.

## 0. 원칙 (기존 그대로 + 추가)
- 모델은 증인, 점수는 코드. 맥락은 점수를 **더하기만** 한다.
- 클라우드는 사용자가 버튼을 누를 때만 간다. `requestCloud()`가 유일한 진입점이다. 맥락을 붙여도 마찬가지다.
- **추가**: 앱 안 검사는 **어떤 경우에도 Chrome을 자동으로 열지 않는다**. 사용자가 확인하려고 온 것이기 때문이다.
- **추가**: 클립보드는 [붙여넣기]를 누를 때만 읽는다. 앱을 열 때 자동으로 감지하는 배너는 만들지 않는다.
- **추가**: 서버는 사용자 맥락을 저장하지 않는다. 캐시, 로그, trace에 원문이 남지 않는다. 받은 요청을 처리하는 메모리 안에서만 쓴다.

| B | **공유 시트** `ACTION_SEND text/plain` → "RedFlag로 검사" | 카카오톡 등의 메시지 → [공유]. 공유된 글 전체가 입력이 된다. | 4 |
| C | **텍스트 선택 메뉴** `ACTION_PROCESS_TEXT` → "RedFlag로 검사" | 선택한 글이 입력이 된다(읽기 전용, 결과를 돌려주지 않음). | 4 |

| E | **최근 기록 행 탭** | 저장된 판정을 보여 준다(`showStored`). [다시 검사]를 누르면 새로 분석한다. | 2 |

- 외부 진입(B, C)은 **UI 없는 트램펄린** `ShareEntryActivity`(exported)로 받는다.
  - 이 트램펄린은 `EXTRA_TEXT`와 `EXTRA_PROCESS_TEXT`만 읽어 비공개 `CheckActivity`로 넘긴다.
  - 그래서 외부 앱이 내부 전용 extra(기록 id, 상황 설명)를 넣어도 무시된다.
- 공유 출발 앱은 `ShareCompat.getCallingPackage()`에서 찾고, 없으면 `referrer`로 찾는다. 결과는 `ContextSources.classify`로 분류한다.
  - 둘 다 못 찾으면 "알 수 없는 앱"으로 둔다.
  - 그다음 기존과 같이 알림 버퍼에서 링크 호스트로 찾는다(30분, 동의된 경우만).
  - 카카오톡 공유에서 이 값이 실제로 잡히는지는 폰 단계에서 측정한다.

## 2. 입력에서 URL 찾기 — `UrlExtractor` (android/core, 계약 벡터)
`contracts/url_extract_vectors.json` 약 40건을 둔다. 클라우드는 이미 정해진 URL 하나만 받으므로 Python 쌍둥이는 필요 없다.

| 규칙 | 예 |
|---|---|
| `http(s)://`, `www.`, 스킴 없는 도메인을 인식한다. 스킴이 없는 도메인은 PSL로 등록 도메인이 되는 것만 인정한다(`3.5`, `a.b` 제외). | `safepay-escrow.shop/pay` → https |
| **한글 붙음**: 호스트는 `[A-Za-z0-9.-]`(또는 IDN 라벨 + 유효 TLD)에서 끝나고, 경로는 공백이나 한글 음절에서 끝난다. | `https://abc.kr/x에서 확인` → `https://abc.kr/x` |
| **끝 문장부호**: `. , ; : ! ? … 」 』 " ' ”`를 떼고, 짝이 맞지 않는 닫는 괄호를 뗀다. | `(https://a.com/p).` → `https://a.com/p` |
| 감싼 형태: `<url>`, 마크다운 `[글](url)` | |
| **디팽(무력화 표기) 해제**: `hxxp(s)://`, `[.]`, `(.)`, `[dot]` | `hxxps://evil[.]com` |
| 고유 URL은 최대 5개, 나온 순서를 유지한다. 정규화한 URL로 중복을 없앤다. | 단축 URL과 대상 URL은 별개로 센다. |
| 제외: http(s)가 아닌 스킴(`javascript:`, `intent:`, `file:`, `data:`), loopback/link-local(`127.*`, `169.254.*`, `::1`, `localhost`). | 사설 IP(192.168 등)는 게이트에 넘긴다(ip_host). 로컬 데모 페이지도 이 경로를 쓴다. |
| 입력은 4,000자에서 자른다. | |

출력: `Extracted(urls: List<String>, message: String?, defanged: Boolean)`.
`message`는 URL을 뺀 나머지 글로, 맥락으로 쓴다(§4).

## 3. 검사 모드 — `CheckActivity` (기존 분석 화면 재사용)
`LinkHandlerActivity.showAnalysis`의 배선(AnalysisController, 소스 분류, ContextActions, ComposeView)을 공용 `AnalysisHost`로 뺀다.
링크 탭과 앱 안 검사는 `AnalysisMode { LINK, INSPECT }`만 다르다.

| | 링크 탭 (기존 LINK) | 앱 안 검사 (INSPECT) |
|---|---|---|
| 알려진 사이트 (Gate Pass: brand/tranco) | 바로 Chrome으로 연다. | 결과 화면에 "알려진 사이트예요 (예: 네이버)"를 띄우고 [그래도 자세히 검사]와 [Chrome에서 열기] 버튼을 준다. |
| 안전 판정 캐시 (Pass: cache) | 건너뛴다. | **무시하고 새로 분석한다**(`Gate.evaluate(raw, useSafeCache = false)`). 결과는 같은 규칙으로 캐시에 쓴다. |
| 단축 URL | 대상을 풀어 분석한다. | 같다. 화면에 `bit.ly/3xY → safepay-escrow.shop/pay` 체인을 보여 준다. |
| 안전 결과 | 0.9초 뒤 Chrome으로 자동 이동한다. | **자동 이동이 없다.** [Chrome에서 열기]와 [닫기] 버튼을 준다. |
| 위험 결과 | [돌아가기](차단 목록에 추가)와 [그래도 열기] | [닫기](같은 차단 목록에 추가: 나중에 탭하면 즉시 경고)와 [그래도 열기] |
| 분석 중 [건너뛰기] | 건너뛰고 Chrome을 연다. | [취소]: 분석을 멈추고 닫는다(Chrome을 열지 않음). |
| Ignore (링크 아님) | — | 홈 카드에 "링크를 찾지 못했어요"를 바로 표시하고 화면을 이동하지 않는다. |
| 맥락 "사이트당 1회" 제한 | 적용한다. | 사용자가 시작한 검사라 **적용하지 않는다**. |
| 고급 분석 버튼 | 있다(요청 시 모드). | 같다. 사용자 맥락 고지가 붙는다(§5.5). |

여러 URL을 찾으면 홈 카드에 칩으로 바로 보여 준다(입력 중 300ms 디바운스, 정규식만 쓰고 네트워크 없음).
사용자가 하나를 고른다. 분석 뒤 결과 화면 아래에 "다른 링크 검사" 칩으로 남는다.
공유와 텍스트 선택으로 들어온 경우에는 `CheckActivity` 첫 화면이 같은 칩 선택 화면이다. 링크가 0개면 "링크를 찾지 못했어요"와 [닫기]를 보여 준다.

## 4. 붙여 넣은 글 = 사용자가 건넨 맥락
- 입력칸에서 URL을 뺀 나머지 글(`message`)을 맥락으로 쓴다.
  - 넣는 곳은 **`<untrusted_conversation>`** 메시지 1개다: `ConvMessage(sender="붙여넣은 메시지", text=mask(…), hasLink=true)`.
  - 받은 메시지는 사기범이 쓴 글일 수 있으므로 데이터로만 다룬다. Turn 3 프롬프트가 이미 이렇게 정의한다.
  - 300자를 넘으면 URL 주변 300자 창만 쓴다(`limits.message_chars`).
- 홈 카드의 **[+ 상황 설명 추가 (선택)]** 칸은 사용자 자신의 말이다.
  - 넣는 곳은 **`<user_statement>`**: `UserAnswer(U1, [], text)`. 기존 [상황 직접 입력]과 같은 경로다.
- **동의 카드가 없다.** 사용자가 스스로 건넨 것이기 때문이다.
  - 분석 화면에 "붙여넣은 메시지를 상황 분석에 사용 중 · [빼기]" 칩을 보여 준다(기본 켬, §10-4).
  - [빼기]를 누르면 Turn 3 전에 빠진다. 고급 분석에도 보내지 않는다.
- 흐름: Turn 1 → ① 코드 판단 → 다음 표의 갈래 → 코드가 가산.

  | ① 코드 판단 | 붙여 넣은 글이 있을 때 |
  |---|---|
  | 제외 (알려진 사이트, Safe Browsing 히트, 85점 이상) | 맥락을 쓰지 않는다. 진짜 네이버 페이지에 사기 시나리오 점수가 붙는 오해를 막는다. 화면에는 "알려진 사이트라 상황 분석은 생략"을 표시한다. |
  | 필요 / 괜찮음 | Turn 2는 **질문이 필요한지만** 본다. 자동 맥락 요청은 무시한다(메시지를 이미 받았음). 그다음 Turn 3로 간다. |

- "다시 묻지 않기"는 질문 카드만 막는다. 붙여 넣은 글을 판단하는 것은 그대로 진행한다. 맥락 분석기를 끄면(설정) 붙여 넣은 글도 쓰지 않는다.

## 5. 사용자 맥락 → 고급(정밀) 분석
### 5.1 무엇을 보내나
| 항목 | 보냄 | 형태 |
|---|---|---|
| 직접 입력한 상황 설명, 질문 답 (U1–U4 칩, 자유 입력) | **예** | 칩 id + 글. 숫자는 `#`로 가린다(`ContextText.mask`). 각 300자, 최대 4개. |
| 앱 안 검사에서 붙여 넣거나 공유한 메시지 | **예** | 마스킹한 글 1개, 300자 |
| 출발 앱 **종류** | 예 | `messenger/sms/mail/browser/qr/unknown` (패키지 이름은 보내지 않음) |
| 기기의 맥락 판단 (Turn 3 결과) | 예 | enum만: scenario, consistency, sender_risk, guided |
| 자동 수집 대화 (알림에서 읽은 메시지) | **아니오 (추천, §10-1)** | 판단 enum으로만 반영된다. 동의 화면의 약속("메모리에만 두고 밖으로 보내지 않아요")은 그대로 지킨다. |

### 5.2 요청 형식 (`POST /v1/analyze`에 추가)
```json
"user_context": {
  "source_category": "messenger",
  "statements": [{"question_id": "U4", "chip_ids": ["yes_trade"], "text": "판매자가 안전결제로 하자고 링크 보냄"}],
  "pasted_messages": [{"text": "[Web발신] 안전결제 진행 → https://safepay-escrow.shop/pay 계좌 ###-####-####"}],
  "device_judgment": {"scenario": "used_trade_escrow", "consistency": "mismatch", "sender_risk": "unknown_sender", "guided": false}
}
```
- 기기: `CloudContext.build(...)`(android/core, 순수 함수)가 마스킹, 길이 제한, 개수 제한을 적용한다.
- 서버: pydantic `UserContext`로 enum과 길이를 엄격히 검증하고, 실패하면 422를 돌려준다.
  - 같은 `mask`를 Python 쌍둥이로 **한 번 더** 적용한다(심층 방어).
  - `followup_vectors.json`에 `cloud_context` 그룹을 추가해 두 구현이 같은 출력을 내는지 검사한다.

### 5.3 서버: 페이지 분석과 맥락 판단을 분리 (추천, §10-2)
```
요청 ─┬─ ① 페이지 단계 (지금 그대로): 샌드박스 → Opus 에이전트 → features
      │     캐시 키 = URL, 맥락이 섞이지 않는다. 같은 URL을 다시 요청하면 캐시를 쓴다.
      └─ ② 맥락 단계 (신규, user_context가 있을 때만): Opus 1회, 도구 없음, submit_context 강제
            입력: <analysis> (코드가 계산, 신뢰: page_domain, 미리 계산한 level, claimed_brand, page_type,
                   requested_actions, official_domain_found)
                  <untrusted_conversation> (붙여 넣은 메시지)
                  <user_statement> (사용자 설명)
            출력: scenario / consistency / sender_risk / evidence (Turn 3과 같은 어휘)
            → 코드가 증거 문구가 입력에 글자 그대로 있는지 확인한다(기기와 같은 검사).
      ③ 병합 (코드, 더하기만): 기기 판단과 클라우드 판단 중 위험한 쪽
            scenario: 클라우드 값, 클라우드가 none이면 기기 값
            consistency: mismatch > unclear > consistent
            sender_risk: impersonated_org > unknown_sender > unclear > known_contact
            guided: 칩 guided OR (링크 메시지 && 모르는 발신자) OR 기기 guided
      ④ report.scoring_input(..., context=병합 결과) → 기존 v4 맥락 규칙(이미 쌍둥이와 벡터가 있음)
```
- **왜 분리하나**:
  1. 캐시는 URL 단위이고 여러 사용자가 공유한다. 한 사람의 맥락이 다른 사람의 페이지 판정에 섞이면 안 된다.
  2. 사기범이 쓴 붙여넣기 글이 페이지 feature 추출을 조종하지 못한다(인젝션 격리).
  3. 기기 구조(Turn 1 페이지 / Turn 3 맥락)와 같아서 어휘와 규칙이 하나로 유지된다.
  4. 비용은 Opus **+1회**다. 캐시가 맞으면 1회만 쓴다.
- 프롬프트 `contracts/opus_context.txt`의 FIELDS 절은 `gemma_context.txt`와 **글자 그대로 같게** 둔다. 테스트로 어휘가 어긋나지 않게 고정한다.
- 실패 처리(D3 유지): 맥락 단계가 시간 초과, 한도, 형식 오류로 실패하면 기기 판단 enum만으로 병합한다. trace에는 "cloud context judgment unavailable, using device judgment"를 남긴다.
  - 맥락 때문에 점수가 내려가는 경로는 없다(병합은 위험 쪽, 규칙은 가산뿐).
  - 기기 화면도 이미 기기와 클라우드 중 더 엄격한 판정을 보여 준다(`currentReport`).
- 페이지 단계가 features 없이 끝나면(오류나 시간 초과) 맥락 단계를 건너뛰고 기기 판단만 쓴다. 이때 결과는 analysis_incomplete로 '안전'이 될 수 없다.
- 결과: `RiskReport` 스키마는 바꾸지 않는다.
  - 맥락 규칙은 red_flags에 `source: "opus+rule"`로 들어가고, 증거 문구는 최대 2개, 각 15단어 이하다.
  - trace의 "context" 단계에는 개수와 enum만 남긴다(`statements=1 pasted=1 · scenario=used_trade_escrow(cloud) …`).

### 5.4 서버에 남는 것
- `store`(sqlite)에는 ①의 페이지 묶음만 들어간다. `user_context`는 어디에도 쓰지 않는다.
- 테스트:
  - 요청 후 DB 전체를 덤프해서 붙여 넣은 글의 부분 문자열이 없는지 본다.
  - 모든 trace detail에도 원문이 없는지 본다.
- 로그에는 요청 본문을 남기지 않는다(현재 uvicorn 기본값 유지를 테스트로 고정).

### 5.5 기기: 언제, 어떻게 보내나
- 사용자가 [정밀 분석]을 누르면 `requestCloud()`가 동작한다.
  - 맥락 단계가 진행 중이면(질문 카드가 열려 있거나 Turn 3 중) **끝날 때까지 기다렸다가** 그 시점의 맥락으로 보낸다.
  - 기다리는 동안 클라우드 카드에 "질문에 답하거나 건너뛰면 시작해요"를 표시한다.
  - 사용자가 이미 누른 요청이므로 자동 전송이 아니다.
- 버튼 아래에 고지 한 줄을 둔다. 확인 창은 따로 띄우지 않는다(§10-3).
  ```
  [ 🔍 정밀 분석 (클라우드) ]
    함께 보냄: 상황 설명 1 · 붙여넣은 메시지 1 (숫자 가림)   보낼 내용 보기 ›
  ```
  [보낼 내용 보기]는 실제로 보낼 마스킹된 글을 그대로 보여 준다.
- 클라우드 결과가 나온 뒤 사용자가 설명을 더하면:
  - 기기 판정은 기존대로 다시 계산된다.
  - 클라우드 카드에 [설명을 더해 다시 정밀 분석]이 나타난다. 이것도 사용자가 눌러야 하며, 캐시가 맞으면 Opus 1회다.
- `NoAutomaticCloudTest`를 확장한다. `CloudContext.build`와 `g.cloud.analyze`는 `requestCloud()` 안에서만 부를 수 있다.

## 9. 단계
1. **core**: `UrlExtractor` + 벡터, `Gate.evaluate(useSafeCache)`
2. **앱 안 검사**: `AnalysisHost` 추출, `CheckActivity`(INSPECT), 홈 카드(칩, 상황 설명), 기록 탭, 붙여넣은 글을 맥락으로 사용
3. **맥락 → 클라우드**: 계약(`opus_context.txt`, `cloud_context`/`context_merge` 벡터), 백엔드(요청 모델, 맥락 단계, 병합, `scoring_input(context)`, 저장 금지 테스트), 앱(`CloudClient` 본문, 맥락 단계 대기, 고지, 다시 분석), 문구 변경. 링크 탭 경로에도 똑같이 적용한다.
4. 공유 트램펄린, `PROCESS_TEXT`, 앱 바로가기
5. 폰 시연과 측정, dev-log/PROGRESS.md 기록, 단계마다 로컬 커밋

범위 밖: QR 이미지 스캔, 여러 링크 한꺼번에 검사, 클립보드 자동 감지 배너, 페이지 에이전트에 맥락을 넣어 조사 방향을 정하는 것(§10-2 대안).
